## Terminal performance

Measure every change with `scripts/terminal-bench.sh` and `scripts/terminal-e2e.sh` (`WOOLOO_E2E_LOAD=N` to measure under load); see `docs/perf/README.md`. wooloo draws every frame Herdr sends (about 43 fps). On a 113×48 grid, arrival to draw takes about 0.8–1.5 ms at p50 and a keystroke reaches the draw in about 0.8 ms; the display then adds an estimated 12–15 ms at 120 Hz. Kitty images cost wooloo little. A tab switch draws 9–13 ms after the click, a two-pane split streams without dropped frames, and the stream thread no longer stalls under machine load. What remains is mostly Herdr's side and the display refresh.

- [ ] Ask Herdr to keep scrolled patches while graphics are on screen. With Kitty images visible, Herdr 0.9.3 sends a complete surface every frame (about 39 KB at 113×48) plus each new image, 11 times the bytes of the same output without images; wooloo's own cost stays low (draw 0.14 ms at p50, main thread 1.2% busy). See `docs/perf/README.md`, "Graphics". In Herdr's source (v0.9.3), the retained render path sends a complete surface whenever the client's last surface or a changed pane has placements (`src/server/headless/retained_surface.rs`, around lines 376–398 and 516–527), even when the graphics did not change, because a patch (`PaneSurfacePatch`, `src/protocol/wire.rs`) and a scrolled patch carry no graphics. `surface_delta` carries graphics but finds no scrolls, so scrolling output falls back to complete surfaces anyway. An issue is drafted: send the (scrolled) patch when the graphics did not change, or let patches carry the graphics scene behind a capability.
- [ ] Find what limits Herdr to about 43 fps under streaming output. A bare endpoint client that draws nothing receives about 56 frames a second from the same workload, so it is not a fixed cap. In Herdr's source (v0.9.3), renders are at least 16 ms apart (`MIN_RENDER_INTERVAL`, `src/app/mod.rs`), which allows about 56–60 a second. Each client has a render lane of one frame, written by a blocking thread with the system's default socket buffers (8 KB on macOS); a frame rendered while the previous one is still being written is dropped, and the client then gets a complete surface (`src/server/client_transport.rs`, `retained_surface.rs`, `headless.rs`). A larger receive buffer on wooloo's side does not help: an AF_UNIX writer on macOS can queue only its own send buffer, 8 KB, whatever the reader's receive buffer (checked with a socket pair). Next: count complete surfaces received during `ascii` (drops show up as complete surfaces mid-stream) and run Herdr with `HERDR_RENDER_PROF=1`, whose counters include deferred recipients and full renders. An issue is drafted, to post with those numbers.
